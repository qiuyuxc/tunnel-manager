# 安卓本地 Cloudflare 亚太候选段筛选（临时原型）

问题：从当前安卓设备的网络出发，能否从 Cloudflare 官方 IPv4 范围中找到实际进入亚太节点、多个地址都能稳定访问业务域名的 `/24` 候选？它用于筛选待验证网段，不接入生产面板，不修改 DNS。

仅依赖 Go 标准库。在仓库根目录运行：

```sh
go run backend/experiments/cf-prefix-survey/main.go \
  -ranges /path/to/cloudflare-ips-v4.txt \
  -seeds /path/to/controls.txt \
  -out /path/to/existing-empty-output-directory \
  -host your-business.example.com
```

官方 IPv4 来源为 <https://www.cloudflare.com/ips-v4>。`controls.txt` 可省略，也可以放少量已知 IP 作对照，每行一个，必须位于输入范围内。输出目录必须存在；脚本拒绝覆盖 `observations.jsonl` 或 `summary.json`。

## 分阶段测量

1. 将较大的输入段划为 `/20` 小区块，每块随机取两个不同 `/24`，各测一个 IP；小于 `/20` 的段按实际大小抽样。加入已知对照 IP。单次最多 1024 个初筛请求，并非逐个扫描全部地址。
2. 请求固定 IP 的 `/cdn-cgi/trace`，使用业务域名的 Host/SNI 和正常证书校验，依据实际 `colo` 判断入口。只有代码允许表中的亚太节点进入后续阶段；欧美和未知代码不进入候选。允许表涵盖东亚、东南亚、南亚及大洋洲的已知节点，不保证穷尽所有新节点代码。
3. 初筛按耗时取最多 32 个不同 `/24`，再加入成功进入亚太的对照段。每段三个地址，各做三次 GET `/`；业务响应中的 CF-Ray 节点也必须为亚太。
4. 从九次全部成功且为亚太的段中，按 P90、再按中位数取最多 12 段。每段另取两个从未测过的新地址，各测三次。
5. 新地址六次也全部通过的段才进入最终候选。每段最终包含五个地址、十五次业务观测；只证明这些样本在本次网络下的表现，不能保证段内剩余地址或其他运营商网络。

可将命中亚太的小区块拆为逐个 `/24` 的输入文件，再运行一次，补足第一次稀疏抽样遗漏的相邻段。必须核对这些子段属于官方列表，仍按实测节点过滤，不能因邻段命中就假定它也位于亚太。

## 请求与输出口径

- 默认每秒最多 5 次新连接、并发 8，可调低。TCP+TLS 共享 3 秒预算，握手后 HTTP 再有 3 秒预算。
- 固定目标 IP、HTTP/1.1、冷 TCP/TLS 连接，不跟跳转；业务探测到响应头即停止，trace 只读少量文本。
- 完整耗时到收到响应头结束，不代表页面或文件下载完成。P90 使用成功观测的 nearest-rank 定义，失败单独保留且不进入推荐。
- 初筛使用 trace 耗时，不能拿它代替业务请求耗时；后两个阶段使用同一业务路径 `/`。
- 原始观测逐条追加到 `observations.jsonl`。`summary.json` 记录参数、地区分布、阶段评分和最终名单；只有 `complete=true` 才表示完整结束。
- 25 分钟自动停止，可用 SIGINT/SIGTERM 取消。未知节点代码、未测区域和超时样本都不能据此判定永久不可用。
- 使用本机原始 socket，不读取 HTTP 代理环境变量；系统 VPN 或路由仍可能影响出口。记录实际本地地址，网络类型由设备状态和用户反馈确认。

本原型沿用分阶段实测方式，不添加测试套件。运行结论及限制见同目录 `NOTES.md`。
