# 首次单机实测：2026-10-08

这次短时对照支持继续验证“多次测量后按完整 HTTPS 耗时选择”：独立复测中，新方法的耗时中位数比旧方法低约 40.2%，最慢请求低约 28.9%。三组成功率相同，都是 9/9。它不能证明三网访问改善，也不足以直接接入自动 DNS 更新。

## 实验记录

- 观测点：用户现有 BGP 服务器 `47.116.188.72`，Linux x86_64；从服务器主动连接候选 IP。
- 北京时间：2026-10-08 12:04:36.903 至 12:08:08.807，约 212 秒。
- 业务目标：固定候选 IP，Host/SNI 均为 `tm.kukie.cn`，HTTPS GET `/`，正常校验证书，接受 HTTP 200。
- 仅测建立连接、TLS 握手和收到 HTTP 状态行的时间；不包含 DNS 查询，也不代表页面加载或正文下载速度。
- 52 个候选、20 个不同 `/24`：每段随机抽 2 个，加入最近入选的 10 个及指定对照 `.229.3/.6`，去重；随机种子 `20261008`。
- 每个候选训练 5 次；每组冻结 3 个 IP，再各复测 3 次。三组并集为 7 个 IP，共发出 260 次训练请求和 21 次独立复测请求，总计 281 次。
- 每秒最多启动 2 次连接、并发 4、轮间隔 10 秒；TCP+TLS 共享 3 秒超时，HTTP 阶段另有 3 秒超时。
- 训练成功 259/260：`172.64.229.6` 第一轮 HTTP 阶段超时，后四轮成功。独立复测 21/21 成功。
- 未调用外部付费测量平台；只有既有服务器产生的少量请求流量。未触发面板扫描，未修改生产配置或 DNS，未新增定时任务。独立进程已结束。

## 学到了什么

单次很快的 IP，后续不一定仍快。例如 `104.18.37.131` 首次完整耗时仅 352.9ms，独立复测中位数却是 899.0ms。相反，`104.18.43.11` 首次为 1437.0ms，五次训练中位数为 368.8ms，独立复测中位数为 398.6ms。这次多次观测比只改计时口径更有帮助。

本次多次测量排名前三本来就属于不同 `/24`，分散规则没有改变入选集合。因此这次没有测出“网段分散本身”的额外收益；不同网段也不代表独立路由或覆盖三个运营商。

当前算法优先成功比例，其次成功请求中位数；最慢耗时只在中位数相同时用于排序。它仍可能保留偶发明显尖峰的 IP，例如上述 `104.18.43.11`，并没有实现尾延迟惩罚。不要将这次较低的最慢耗时解读为算法已经保证尾延迟。

## 限制与后续判断

- 只有一个出口、一个中午时段，候选仅为抽样，每个入选 IP 只有三次独立复测；没有统计显著性或三网覆盖结论。
- 旧方法只在这 52 个候选上重现单次 HTTP 排序，并统一取 3 个、低速发请求。没有重跑生产全量扫描，也不是与当前生产 10 个 DNS 地址的直接对照。
- 多次训练请求量是单次训练的 5 倍。本次限制候选数以控制开销，不应直接扩成全量网段每个地址都测五次。
- 最近入选的 IP 只作为候选；历史评分、保留旧 IP、切换迟滞均未实现。此次新组选中的 IP 与最近入选的 10 个没有重合，也不能因此直接整批替换。
- 下一步适合用同一脚本在晚高峰等其他时段复测，先固定候选与参数比较时段变化，再考虑扩展样本。只有效果可重复，才讨论面板集成及减少切换；本次没有安排自动复测。
